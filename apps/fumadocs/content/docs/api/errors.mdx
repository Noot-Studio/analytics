The Ingestion API uses standard HTTP status codes. A successful ingest returns `202 Accepted`; everything else is an error. Error responses carry a short plain-text message describing the problem.

## Status codes

| Status                      | Message                | Meaning                                                                                                                                                             | What to do                                                                                                                                                                               |
| --------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `202 Accepted`              | —                      | The batch was queued for processing.                                                                                                                                | Success. The response body is `{ "accepted": <n> }`.                                                                                                                                     |
| `400 Bad Request`           | `invalid payload`      | The JSON body didn't match the expected shape (missing `events`, empty array, more than 500 events, an event missing `type`/`session_id`, or a field out of range). | Fix the payload to match the [events schema](/docs/api/events#body).                                                                                                                     |
| `400 Bad Request`           | `properties too large` | An event's `properties` object exceeded 16 KB once JSON-encoded.                                                                                                    | Shrink the offending event's `properties`.                                                                                                                                               |
| `401 Unauthorized`          | `invalid api key`      | The `x-api-key` header was missing, unknown, or belongs to a revoked key.                                                                                           | Check the header and that the [key](/docs/application/api-keys) is active. Newly created keys are effective immediately; revoked/rotated keys can take up to ~5 minutes to stop working. |
| `413 Payload Too Large`     | `body too large`       | The request body exceeded 2 MB.                                                                                                                                     | Send fewer events per request (the per-request cap is 500).                                                                                                                              |
| `500 Internal Server Error` | `key lookup failed`    | The platform couldn't verify the API key due to a transient backend error.                                                                                          | Retry with backoff.                                                                                                                                                                      |
| `502 Bad Gateway`           | `publish failed`       | The events couldn't be queued downstream.                                                                                                                           | Retry with backoff.                                                                                                                                                                      |

## Error body

Errors return the message as the response body, with the matching HTTP status. For example, an unauthorized request:

```http
HTTP/1.1 401 Unauthorized
Content-Type: text/plain

invalid api key
```

## Handling errors

- **`4xx` errors are your responsibility to fix** — the same request will keep failing. Validate payloads and check your key before retrying.
- **`5xx` errors are transient.** Retry with exponential backoff and jitter. Because ingestion is asynchronous, a brief delay is fine — buffer events client-side and resend.
- **Don't hammer on `401`.** A revoked or wrong key will not start working on retry; surface it instead.

```js
async function sendEvents(batch) {
  const res = await fetch("https://ingest.sbox-analytics.com/v1/events", {
    method: "POST",
    headers: {
      "x-api-key": "pk_your_publishable_key",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ events: batch }),
  });

  if (res.status === 202) {
    return; // queued
  }

  if (res.status >= 500) {
    throw new Error("transient ingestion error — retry with backoff");
  }

  // 4xx — fix the request or the key; do not blindly retry.
  throw new Error(`ingestion rejected (${res.status}): ${await res.text()}`);
}
```

## Health check

`GET /healthz` is unauthenticated and returns `200 OK` with the body `ok` while the ingestion service is live. Use it for uptime monitoring — it does not touch your data or keys.
