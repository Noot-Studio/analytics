**API keys** are the credentials a [project](/docs/application/workspace#projects) uses to talk to s&box Analytics. Keys are scoped to a single project — every event sent with a key is attributed to that project.

Each key is a pair:

| Part                | Prefix | Purpose                                                                                                                                                                                                                          |
| ------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Publishable key** | `pk_`  | Sent on every ingestion request via the `x-api-key` header. Ships inside your game and authenticates event ingestion.                                                                                                            |
| **Secret key**      | `sk_`  | Shown **once**, at creation (stored only as a hash). Authenticates **read** endpoints — e.g. the [spatial endpoints](/docs/api/spatial) behind the SDK's [in-editor heatmaps](/docs/sdk/heatmap). Keep it out of shipped builds. |

<Callout type="info">
  The publishable key is what your game ships with. The secret key is returned a
  single time at creation or rotation and never shown again — copy it somewhere
  safe immediately.
</Callout>

## Creating a key

1. Open the project you want the key for.
2. Choose **Create API key** and give it a **name** (1–100 chars) — something that identifies where it's used, like `prod-client` or `playtest-build`.
3. Confirm. You're shown the **publishable** and **secret** keys.
4. Copy the **secret key** now — it can't be retrieved later, only regenerated by rotating.

A project holds up to **100 active keys**; revoked keys don't count.

## Managing keys

- **List** — a project shows its active keys, most recent first, with name, publishable key, creation date, and **last used** (handy for spotting stale keys).
- **Revoke** — disables a key permanently; any request using it is rejected with `401 invalid api key`.
- **Rotate** — issues a fresh `pk_`/`sk_` pair for the same key record and invalidates the old one. Use it when a key may have leaked but you don't want to reconfigure everything. The new secret is shown only once.

<Callout type="warn">
  Key validity is cached, so a revocation or rotation can take up to **5
  minutes** to take effect across the ingestion layer. Plan accordingly.
</Callout>

## Security best practices

- **Treat the secret key like a password.** Never commit it, embed it in a shipped client, or paste it into logs or screenshots.
- **The publishable key isn't a secret in the same way** — it ships inside your game and only authenticates ingestion; it can't read your analytics or manage your account. Still, prefer **one key per build/environment** so you can revoke one without affecting others.
- **One key per environment.** Distinct keys for `Development`, `Staging`, and `Production` keep traffic isolated and independently revocable.
- **Rotate on suspicion**, and **name keys meaningfully** so it's obvious which to revoke.
- **Only organization members manage keys.**
