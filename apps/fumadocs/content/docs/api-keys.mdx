**API Keys** are the credentials a [Project](/docs/projects) uses to send events to s&box Analytics. Keys are scoped to a single Project — every event sent with a key is attributed to that Project.

## What API Keys are used for

When your game sends an event to the [Ingestion API](/docs/api), it identifies itself with an API key. The platform looks up the key, resolves it to a Project, and stores the event under that Project. No key, or an unknown/revoked key, means the request is rejected.

Each API key is a pair:

| Part                | Prefix | Purpose                                                                                                                  |
| ------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Publishable key** | `pk_`  | Sent on every ingestion request via the `x-api-key` header. It ships inside your game and authenticates event ingestion. |
| **Secret key**      | `sk_`  | Shown **once**, at creation. Stored only as a hash on our side. Keep it server-side; treat it like a password.           |

<Callout type="info">
  The publishable key is what your s&box game uses to send events. The secret
  key is returned a single time when you create or rotate a key and is never
  shown again — copy it somewhere safe immediately.
</Callout>

## Creating an API Key

1. Open the Project you want the key for.
2. Choose **Create API key** and give it a **name** (1–100 characters) — something that identifies where it's used, like `prod-client` or `playtest-build`.
3. Confirm. You'll be shown the **publishable key** and the **secret key**.
4. Copy the **secret key** now. It cannot be retrieved later — only regenerated by rotating.

A Project can hold up to **100 active keys**; revoked keys don't count toward the limit.

Use the publishable key in your game's analytics configuration. See [API Usage → Authentication](/docs/api#authentication).

## Managing API Keys

### Listing

A Project shows all of its active keys, most recent first, with each key's **name**, **publishable key**, creation date, and **last used** timestamp. The last-used timestamp is handy for spotting keys that are no longer in use.

### Revoking

Revoking a key disables it permanently. Revoked keys disappear from the list and any request using one is rejected with `401 invalid api key`.

1. Find the key in the Project's key list.
2. Choose **Revoke** and confirm.

<Callout type="warn">
  Key validity is cached for performance, so a revocation can take up to **5
  minutes** to take effect across the ingestion layer. Plan rotations
  accordingly.
</Callout>

### Rotating

Rotating issues a brand-new publishable/secret pair for the same key record and invalidates the previous pair. Use it when a key may have leaked but you don't want to delete the key and reconfigure everything from scratch.

1. Choose **Rotate** on the key.
2. Copy the new **secret key** — like creation, it's shown only once.
3. Update your game/build with the new publishable key.

The old pair stops working once the cache expires (up to ~5 minutes).

## Permissions and security best practices

- **Only Organization members manage keys.** Creating, listing, revoking, and rotating a Project's keys requires membership in the [Organization](/docs/organizations) that owns the Project.
- **Treat the secret key like a password.** Never commit it to source control, never embed it in a shipped client, and never paste it into logs or screenshots.
- **The publishable key is not a secret in the same way** — it travels inside your game and authenticates ingestion only. It cannot read your analytics or manage your account. Even so, prefer a **separate key per build/environment** so you can revoke one without affecting others.
- **One key per environment.** Use distinct keys for `Development`, `Staging`, and `Production` Projects so test traffic and production traffic stay isolated and independently revocable.
- **Rotate on suspicion.** If a key may have leaked, rotate or revoke it immediately. Remember the propagation delay.
- **Name keys meaningfully.** A clear name (`prod-client`, `ci-smoke-test`) makes it obvious which key to revoke when something changes.
