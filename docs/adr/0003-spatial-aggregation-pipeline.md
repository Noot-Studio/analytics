# Client-side spatial aggregation into dedicated rollup tables

Position tracking for dwell, movement-density, and per-player trajectory heatmaps emits one event per sample per player. At a useful sample rate (≥5 Hz) that is thousands of events per player per minute, and the event is the unit of cost (quota counts rows). The existing voxel path stores raw positions in `analytics.events` and bins them at query time (`floor(pos / voxelSize)`), which keeps `voxelSize` flexible on read — but that flexibility is exactly what makes continuous position capture unaffordable: every sample is a stored row forever.

We move the aggregation to the SDK and persist pre-aggregated rows in dedicated ClickHouse tables, keyed so they keep collapsing after ingest.

**Dwell and movement-density** are accumulated per grid cell on the client — `cell = floor(pos / cell_size)`, held in a sparse dictionary — and flushed once per window as a single compact `spatial_cells` batch event (`properties = { kind, cell_size, cells: [[gx,gy,gz,value],…] }`). `kind` is an open metric label — `dwell`, `visits`, or any game-defined scalar — so a new aggregated metric needs only an SDK accumulator and a dashboard label, no server change. Ingest fans each batch into per-cell rows on a dedicated topic; `analytics.spatial_cells` (SummingMergeTree) sums `value`/`hits` across windows and across players for cells sharing `(project, scene, kind, cell_size, gx, gy, gz, day)`. This trades the existing query-time re-binning flexibility for a **fixed capture grid**: cells re-bin coarser (sum whole multiples of `cell_size`) but never finer than capture. Accepted — heatmaps render at a fixed resolution anyway, and the volume reduction is the whole point: a stationary player collapses from ~N samples to one cell row per window, and many players/windows over the same cell sum to one stored row.

**Per-player trajectories** cannot aggregate — identity and order _are_ the signal. They are RDP-simplified (Ramer–Douglas–Peucker) on the client to drop collinear points, flushed as a `trajectory` batch (`properties.points = [[x,y,z,t_ms],…]`), and fanned into ordered rows in `analytics.trajectory_points` (plain MergeTree, ordered by `project, scene, player, session, timestamp, seq`). RDP keeps exact positions — no grid — so trajectories lose redundant points, never spatial precision. They stay the most expensive of the three; the SDK warns on enable.

Consequences: the raw-position voxel path (`analytics.events` + `buildVoxelsQuery`) stays for ad-hoc and low-volume spatial events; the rollup path serves high-frequency capture. `cell_size` is part of the `spatial_cells` sort key, so a scene mixing capture resolutions is safe to store but not summable across sizes. The two event types `spatial_cells` and `trajectory` are contract-level canonical names; ingest routes them away from the `events` topic to dedicated topics, so spatial-cell rows never land in the raw events table.
